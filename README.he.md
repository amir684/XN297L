# ESP32 + XN297L — קישור טקסט לבדיקה

שני לוחות ESP32, כל אחד עם מודול XN297L. אחד משדר שורת טקסט כל שנייה, השני מדפיס
אותה לסריאל. הקוד זהה בשני הלוחות — רק ה-environment של PlatformIO משתנה.

הדרייבר נכתב מול **Panchip XN297L Technology Reference Manual, v4.8, May 2016**.
הפניות לסעיפים בהערות שבקוד מתייחסות למסמך הזה.

## סביבות

| env | לוח | תפקיד |
|---|---|---|
| `tx` | ESP32 WROOM | יוזם |
| `rx` | ESP32 WROOM | משיב |
| `tx_c3` | ESP32-C3 SuperMini | יוזם |
| `rx_c3` | ESP32-C3 + OLED 0.42" | משיב, עם מסך סטטוס |
| `scan` | כל אחד | סריקת רגיסטרים לחיפוש RSSI |

## חיווט ל-ESP32-C3 (`tx_c3` ו-`rx_c3`)

| XN297L | ESP32-C3 |
|--------|----------|
| `3V3`  | `3V3` |
| `GND`  | `GND` |
| `CLK`  | `GPIO4` |
| `MISO` | `GPIO3` |
| `MOSI` | `GPIO10` |
| `CSN`  | `GPIO7` |
| `CE`   | `GPIO1` |
| `IRQ`  | `GPIO0` |

`GPIO5`/`GPIO6` שייכים לצג; `GPIO2`/`8`/`9` הם strapping; `GPIO20`/`21` הם ה-UART.
הפינים למעלה נמנעים מכולם. ה-C3 מנתב SPI דרך מטריצת ה-GPIO, אז הבחירה חופשית.

**אותו פינאאוט לשני לוחות ה-C3**, גם ל-SuperMini שאין לו צג ויכול היה לפנות את
`5`/`6` — כך רתמת חוטים אחת מתאימה לשניהם והחלפת תפקידים לא דורשת חיווט מחדש.

ל-SuperMini יש נורית מובנית על `GPIO8` (active low) שמהבהבת בכל שידור: הבזק קצר
= ACK, ארוך = כשל. בלוח בלי צג זו הדרך היחידה לראות שהוא חי בלי לפתוח מוניטור.

### דפי הצג — לחצן BOOT מחליף ביניהם

`GPIO9` בלוח ה-OLED. חמישה דפים במחזור:

| דף | מה |
|---|---|
| `OVERVIEW` | מונה, טמפ' ממורכזת, בר עוצמה, שני ה-RSSI, מצב קישור |
| `TEMP` | הטמפרטורה של ה-TX בספרות גדולות על כל הצג |
| `SIGNAL` | ה-RSSI בגדול, הממוצע, ובר רחב |
| `STATS` | נקלטו / אבודות / זמן פעילות |
| `GRAPH` | גרף טמפרטורה של 68 הדגימות האחרונות, בקנה מידה אוטומטי |

הגרף מותח את עצמו לטווח שקיים בפועל — על שבב שנודד מעלה בכמה דקות, קנה מידה
קבוע היה מצייר קו ישר ולא אומר כלום. המספר בפינה הימנית העליונה הוא מרווח
הטמפרטורות שהגרף פורש.

הלחצן נדגם בכל סבב של `loop()`, אז הדף מתחלף מיד ולא ממתין לחבילה הבאה.

`GPIO9` הוא ה-strapping pin של ה-boot. לקרוא אותו כקלט בזמן ריצה זה תקין;
להחזיק אותו לחוץ תוך כדי reset מכניס את הצ'יפ למצב צריבה — זה הלחצן עושה את
עבודתו המקורית, לא תקלה.

```
pio run -e tx_c3 -t upload --upload-port COM7
pio run -e rx_c3 -t upload --upload-port COM6
```

**שתי מלכודות בצג הזה**, שתיהן מטופלות ב-[src/main.cpp](src/main.cpp):

1. הפאנל הוא חלון **72×40 בתוך בקר SSD1306 של 128×64**, בהיסט `(28,24)`. מי שמנהל
   אותו כ-128×64 רגיל מקבל תמונה מחוץ למסך. הקוד משתמש ברכיב הייעודי של U8g2
   שמטפל בהיסט.

   **אבל הפאנלים לא חתוכים אותו דבר**, ובלוח הזה צריך תיקון בשני הצירים:

   **אופקית** — החלון מתחיל שתי עמודות מאוחר יותר ממה ש-U8g2 מניח, אז התו
   הראשון בכל שורה נחתך. `OLED_X = 2` מזיז את הציור. הרוחב השימושי מתכווץ
   בהתאמה, כך ששום דבר לא בורח מימין.

   **אנכית** — התמונה יושבת כמה שורות נמוך מדי והתחתית נחתכת. את זה **אי אפשר**
   לתקן בציור: הבאפר הוא 40 שורות והתוכן כבר מתחיל בשורה 0, אין לאן לעלות.
   הפתרון הוא **רגיסטר `0xD3` של ה-SSD1306** — display offset, שקובע מאיזו שורת
   COM הפאנל מתחיל להציג, כלומר מזיז את החלון עצמו. ‏`OLED_COM_OFFSET = 12`
   נמדד על הפאנל הזה.

   אם תחליף פאנל, `OLED_CALIBRATE = true` מריץ סריקה: היא מציירת מסגרת סביב כל
   הבאפר ומעלה את ההיסט מ-0 ל-32, שנייה ומשהו לכל ערך, עם המספר גדול על המסך.
   הערך שבו המסגרת יושבת צמודה לארבע הפינות הוא התשובה.
2. נתיב ה-I2C-בחומרה של U8g2 קורא ל-`Wire.begin()` **בלי ארגומנטים**, כלומר עם
   ברירת המחדל של הצ'יפ ולא של הלוח. לכן הקוד משתמש ב-I2C בתוכנה עם פינים
   מפורשים.

בעלייה מודפסת סריקת I2C לסריאל. אם היא לא מוצאת `0x3C`, הפינים לא נכונים — וזה
מפריד מיד בין "פינים לא נכונים" ל"דרייבר לא נכון".

## חיווט (זהה בשני הלוחות)

| XN297L | ESP32 (WROOM) | הערה |
|--------|---------------|------|
| `3V3`  | `3V3`         | טווח האספקה הוא **2.2–3.3V**, מקסימום מוחלט 3.6V |
| `GND`  | `GND`         | |
| `CLK`  | `GPIO18`      | VSPI SCK |
| `MISO` | `GPIO19`      | VSPI MISO |
| `MOSI` | `GPIO23`      | VSPI MOSI |
| `CSN`  | `GPIO5`       | |
| `CE`   | `GPIO4`       | |
| `IRQ`  | `GPIO16`      | מחובר אבל עדיין לא בשימוש (הקוד עובד ב-polling) |

3.3V של ה-ESP32 נמצא **בקצה העליון** של טווח האספקה של הצ'יפ. זה חוקי, אבל זה
מוריד את המרווח שיש לך מול נפילות מתח, ולכן:

- **קבל 10µF בין `3V3` ל-`GND` של המודול**, קרוב ככל האפשר לרפידות. הדאטהשיט
  מראה 1µF ב-designs לדוגמה; 10µF על חוטי breadboard זה לא מוגזם. הרגולטור של
  ה-ESP32 שוקע כשה-Wi-Fi והרדיו מושכים יחד, וזה הגורם מספר אחת לקישור שנופל
  באקראי.
- **חוטים קצרים, מתחת ל-10 ס"מ.** ותרחיק את חוט האנטנה משאר החוטים.

## מה אמור להופיע בסריאל

במשדר:

```
  ESP32 + XN297L  --  TRANSMITTER
SPI self-test PASSED -- the module is alive.
--- XN297L registers ---
  0x00 CONFIG      = 8E
  0x06 RF_SETUP    = 2C
  0x1F BB_CAL      = 0A 6D 67 9C 46
  ...
[     0] tx "Hello XN297L #0" -> ACK  (retransmits: 0)
```

`CONFIG = 8E` זה הסימן שהצ'יפ באמת ב-standby-III ומוכן לשדר — ראה למטה למה הביט
העליון שם הוא הביט הכי חשוב בכל הקובץ. `BB_CAL` אמור לחזור בדיוק כמו למעלה.

במקלט:

```
[     1] rx #0   lost=0   seen=1
```

## על ה-RSSI

רגיסטר `0x09` (`RSSI_RT` 7:4 / `RSSI_SY` 3:0) מוחזר **אפס** במודול הזה, גם
כשקוראים אותו ברגע שהחבילה מזוהה ולפני `R_RX_PAYLOAD`. הדאטהשיט של ה-XN297L
מסמן אותו `09*` ומפנה ל-"software design reference" שפאנצ'יפ מעולם לא פרסמה.

**המסמך הזה נמצא** — הריפו [foldedtoad/xn297_cal](https://github.com/foldedtoad/xn297_cal)
מכיל את `XN297_complete.pdf`, הדאטהשיט הסיני המלא של ה-**XN297**, שבו כל
הרגיסטרים ה"מיוחדים" מתועדים. ה-RSSI מכובה כברירת מחדל מאחורי ביט enable:

| מיקום | שדה | תיאור |
|---|---|---|
| `RF_SETUP` (0x06) ביט 7 | `RSSI_EN` | `1` = מופעל. **reset = 0** |
| `RF_SETUP` ביט 5 | `RSSI_SEL` | `1` = דגימה דרך פילטר |
| `CONFIG` (0x00) ביט 7 | `DATAOUT_SEL` | בוחר מה `0x09` מוציא |
| `RF_CAL` ביטים 48:47 | `RSSI_GAIN_CTR` | `00`=0dB `01`=-6 `10`=-12 `11`=-18 |

**אבל זה ה-XN297, לא ה-XN297L,** ובדיוק שני ביטי ההפעלה מופו מחדש בגרסת ה-L:
`RF_SETUP` ביט 7 הפך לחלק מ-`RF_DR`, ו-`CONFIG` ביט 7 הפך ל-`EN_PM`. לפי
הדאטהשיט של ה-L, אין שם דרך להפעיל RSSI.

### הניסוי שהכריע — הורץ, והתוצאה: XN297L אמיתי

`TRY_RSSI_EN` ב-[src/main.cpp](src/main.cpp#L57) מדליק את `RF_SETUP` ביט 7 בשני
הלוחות. הרצנו אותו. התוצאה:

```
[   1] rx #0   lost=0   seen=1   rssi=00      <- המקלט קיבל
[   1] NO ACK -- the other board did not receive this one
```

**הנתונים עברו, ה-ACK לא חזר, וה-RSSI נשאר אפס.** זה שולל את השערת ה-XN297: אילו
ביט 7 היה `RSSI_EN` הוא לא היה נוגע ב-ACK, וה-`0x09` היה מתעורר.

מה שכן קרה הוא בדיוק ההתנהגות של `RF_DR`: הביט העליון העביר את הקצב ל-`0b10`,
שמסומן **Reserved** בטבלה. שני הלוחות עברו יחד לאותו קצב, ולכן המידע עדיין
מצליח לעבור — אבל חלון ה-ACK מתכייל לפי הקצב (`RX_ACK_TIME` ב-`BB_CAL`: ‏`×16`
ל-2Mbps, ‏`×32` ל-1Mbps, ‏`×128` ל-250K), ובקצב לא מוגדר הכיול נשבר.

**מסקנה: ביט 7 של `RF_SETUP` הוא `RF_DR`, לא `RSSI_EN`. הדרך של ה-XN297 סגורה
כאן.** המתג הוחזר ל-`false`.

הביט השני של ה-XN297, ‏`DATAOUT_SEL` ב-`CONFIG` ביט 7, הוא `EN_PM` בגרסת ה-L —
והוא נדרש לקליטה, אז גם הוא לא פנוי.

נשאר `RSSI_EN` שהוזז לאחד מהרגיסטרים המיוחדים שלא מתועדים ב-L — **וסריקת הביטים
מצאה אותו.**

### סבב ראשון: שלוש "פגיעות", כולן שקריות

הסריקה הראשונה סימנה שלושה ביטים שהזיזו את `0x09` — `0x1B` ביט 21 (`0x91`),
`0x1E` ביט 15 (`0x60`) ו-`0x1E` ביט 16 (`0x04`) — כולם לכאורה עם קליטה תקינה.

**כולן היו ארטיפקט של באג בסריקה.** התנאי ל-"קליטה תקינה" היה ש-`available()`
יחזיר אמת, כלומר שמשהו נחת ב-FIFO. רעש מספק את התנאי הזה בדיוק כמו חבילה. הביטים
האלה הורסים את אימות החבילה, הצ'יפ מתחיל לפענח רעש, ה-FIFO לעולם לא ריק, ו-`0x09`
מתמלא בזבל. כך זה נראה כשמדליקים אחד מהם:

```
[ 34050] rx #572657937    lost=12963   rssi=88
[ 34051] rx #1145315874   lost=17331   rssi=22
```

מונים אקראיים, `lost` מקפץ, והערכים ב-`0x09` הם תבניות ביטים (`88`, `22`, `11`,
`44`) ולא גדלים שנודדים עם המרחק.

### התיקון: אימות אמיתי

לחבילה יש עכשיו `LINK_MAGIC` בראשה, והסריקה סופרת בנפרד `good` ו-`junk`. ביט
נחשב פגיעה רק אם הוא **גם** הזיז את `0x09` **וגם** השאיר חבילות אמיתיות מגיעות.

### סבב שני: `RSSI_GAIN_CTR` ב-`0x1E`

`0x1B` ביט 21 נפל — הוא היה רעש. **שני ביטים שרדו, עם `junk=0`:**

| ביט ב-`0x1E` | `RSSI_GAIN_CTR` | `0x09` |
|---|---|---|
| 15 | `01` = -6dB | `0x66` |
| 16 | `10` = -12dB | `0x06` |

השניים צמודים, והם נוחתים בדיוק במקום שבו `RSSI_GAIN_CTR` יושב במפת השדות של
ה-XN297 (‏`RF_CAL` ביטים 48:47 — מנחית `-0`/`-6`/`-12`/`-18dB` על נתיב ה-RSSI),
אם 24 הביטים של `0x1E` בגרסת ה-L הם 24 הביטים העליונים של ה-`RF_CAL` בן 56
הביטים של ה-XN297. המיפוי מוסק ולא מתועד — אבל הוא **חזה את שני מיקומי הפגיעה
לפני שהסריקה רצה**, והקריאות מתנהגות כמו מנחית: `RSSI_RT` יורד מ-`6` ל-`0` כשהשדה
עולה מ-`01` ל-`10`.

זה גם מסביר את האפס שממנו התחלנו. **כנראה אין ביט enable נפרד ב-L:** ‏`00`, ערך
ה-reset, פשוט אומר "בלי מדידה", וכל ערך אחר מדליק את הגלאי.

### אומת על חומרה

הערך **נודד עם המרחק**: בערך `08` בצמוד, בערך `01` בחדר אחר, ו-`lost` נשאר `0`
לכל האורך. זה מד עוצמה, לא ביט שנדלק.

הניבל השימושי הוא **`RSSI_SY` התחתון, סקאלה 0–15**. ‏`RSSI_RT` העליון קורא `0`
בשימוש רגיל — הוא מדידת זמן אמת, ועד שהתוכנה מספיקה לקרוא את `0x09` הפרץ כבר
נגמר. ‏`RSSI_SY` לעומתו ננעל בסנכרון החבילה ונשאר יציב.

### המחיר: ההיחלשות אמיתית, ועולה רגישות

השדה נקרא בדאטהסיט הסיני **"RSSI 的信号增益衰减的选择位"** — ביטי בחירה של היחלשות
הגבר. **ההיחלשות לא מבודדת לגלאי; היא נופלת על נתיב הקליטה עצמו.**

עם RSSI דלוק בשני הצדדים הקישור התפרק:

```
[   182] ok  retries=2   (no answer)      answers=0/183
[   185] NO ACK -- the other board did not receive this one
```

‏`retries` טיפס ל-2–3, ‏`MAX_RT` נעשה שכיח, ו**התשובה הפסיקה להגיע לגמרי**. החבילה
קדימה שרדה כי ה-auto-ack נותן לה 15 שידורים חוזרים שסופגים את ההפסד; התשובה
נשלחת ב-NOACK ואין לה מרווח כזה, אז היא הצד שנמחק.

### הפתרון: לדגום לסירוגין

ניסיון ראשון היה למדוד רק במשיב. זה עבד, אבל עדיין עלה — `retries` נשאר על `2`
לעומת `0`–`1` בלי RSSI, וצד אחד תמיד הראה `off`.

**המפתח הוא שההיחלשות קיימת רק כל עוד הביטים דלוקים**, וההדלקה היא כתיבת SPI
אחת. אז שני הלוחות מדליקים את הגלאי לסבב אחד מתוך `RSSI_SAMPLE_EVERY` (ברירת
מחדל 4) ורצים ברגישות מלאה בשאר הזמן. שני הכיוונים נמדדים, והקישור מבלה שלושה
רבעים מהזמן בלי שום דבר בדרך.

בין דגימה לדגימה כל צד ממשיך לשדר את הקריאה האחרונה שלו, אז התצוגה יציבה.

`RSSI_GAIN` ב-[src/main.cpp](src/main.cpp#L62): ‏`1` = -6dB (ברירת מחדל, הרגישות
המרבית מבין האפשרויות הפעילות), `2` = -12dB, `3` = -18dB, `-1` = לכבות לגמרי.
‏`RSSI_SAMPLE_EVERY` מווסת בין תדירות המדידה לאיכות הקישור.

כל חבילה נושאת את המדידה של השולח, כך ששני הצדדים מציגים את אותם שני מספרים:

```
[    21] i hear you=6   (mean 6)   you hear me=off   lost=0   seen=22
```

`off` פירושו שהצד השני לא מודד — לא שהוא שומע אותך באפס. לוח שה-RSSI כבוי בו
שולח `0xFF` ולא `0`, בדיוק כדי שההבדל בין "אין מדידה" ל"מדידה של אפס" לא ייעלם.

**תמיד תסתכל על ה-`mean`.** הדגימה הבודדת מקפצת בכמה יחידות בין חבילות עוקבות
כששום דבר לא זז — `7`, `5`, `1`, `2`, `6`, `8` על שולחן יציב. זו מדידת 4 ביט
ולא מכשיר מדידה; הממוצע על 8 דגימות הוא מה שבאמת נודד עם המרחק.

**המספר יחסי ולא מכויל.** פאנצ'יפ מסמנת את ה-RSSI כ-**(测试用)**, "לשימוש בדיקה",
גם בדאטהשיט שכן מתעד אותו. `retries` ו-`lost` נשארים המדדים לטווח ארוך.

### `scan` — סריקת ביט בודד אחרי ה-enable

```
pio run -e tx   -t upload --upload-port COM3    # לוח א ממשיך לשדר
pio run -e scan -t upload --upload-port COM4    # לוח ב סורק
```

הסריקה עוברת על `0x19` (בית), `0x1B` (3 בתים) ו-`0x1E` (3 בתים) — 56 מועמדים,
בערך 90 שניות. כדאי להוריד את `TX_INTERVAL_MS` ל-`100` בלוח המשדר; הסריקה צריכה
לפחות חבילה אחת לכל מועמד.

**למה ביט בודד ולא כוח גס:** שבעה בתים הם 2^56 צירופים. במקום זה הסקיצה קוראת את
ערכי ברירת המחדל של הצ'יפ והופכת **ביט אחד בכל פעם**. כל כתיבה רחוקה בביט אחד
מהמצב התקין — גם חיפוש ממצה יותר, וגם בטוח בהרבה מלזרוק ערכים אקראיים לרגיסטרי
כוונון אנלוגיים.

הסקיצה דוגמת את `0x09` ברציפות ולא רק בקליטת חבילה, כי ביט שמדליק את גלאי ההספק
בזמן אמת עלול באותה נשימה לשבור את הפענוח — וזה עדיין למצוא את ה-enable. כל שורה
מדווחת גם `rx ok` או `rx DEAD` כדי שיהיה אפשר להבחין.

הרגיסטרים מוחזרים לערכי ההפעלה בסוף, והם ממילא נדיפים — ניתוק חשמל מנקה הכל.

**בונוס:** השורות הראשונות מדפיסות את ערכי ברירת המחדל של `0x19`, `0x1A`, `0x1B`
ו-`0x1E`. הם לא פורסמו מעולם ל-XN297L, אז הם שווים תיעוד בין אם הסריקה תמצא משהו
ובין אם לא.

בכל מקרה, שני מדדי האיכות למטה מתועדים ועובדים ולא תלויים ב-RSSI.

שני מדדי האיכות שכן עובדים, ושניהם מתועדים:

- **`retries`** — `ARC_CNT` מתוך `OBSERVE_TX`. כמה שידורים חוזרים נדרשו כדי
  שהחבילה תעבור. 0 = קישור נקי.
- **`lost`** — פערים ברצף המונה בצד המקלט, כלומר חבילות שמעולם לא הגיעו.

## למה התשובה נשלחת בלי ACK

החבילה בכיוון היוזם→משיב היא ACKed, ומשם מגיע `retries`. **התשובה נשלחת
ב-`W_TX_PAYLOAD_NOACK`** (טבלה 7-2, ‏`EN_NOACK` ב-`FEATURE`, אחרי `ACTIVATE` עם
`0x73`).

הסיבה מעשית: כשהתשובה דרשה ACK, היא הגיעה — אבל ה-ACK עליה לא תמיד חזר, והמשיב
שידר אותה עוד 14 פעם לתוך לוח שכבר יצא ממצב קליטה. `ARC_CNT=15` בכל סבב, ו-16ms
של שידור מיותר. התשובה היא טלמטריה בלבד על חילופין שכבר אושרו, אז היא לא צריכה
אישור משלה.

## איך לקרוא את התוצאה

הקוד מפריד בכוונה בין שתי שאלות שונות לגמרי:

**1. האם ה-SPI מחווט נכון?** — `selfTest()` כותב שתי תבניות שונות ל-`TX_ADDR`
וקורא אותן בחזרה. זה עובר רק אם `MOSI`, `MISO`, `CLK` ו-`CSN` כולם נכונים
והמודול מקבל מתח. אם זה נכשל הקוד עוצר ומדפיס dump של הרגיסטרים — dump שכולו
`00` או כולו `FF` אומר שאין תקשורת SPI בכלל.

**2. האם ה-RF עובד?** — זה `ACK` מול `no ACK` בשורות המשדר. ה-auto-ack מופעל,
כך ש-`ACK` הוא הוכחה שהמקלט קיבל את החבילה ושהתשובה שלו חזרה.

הפירוד הזה חשוב, כי הוא מפצל את הבאג: **self-test עובר אבל אין `ACK`** = החיווט
תקין והבעיה ב-RF. במקרה כזה, לפי הסדר:

1. **הרחק את הלוחות זה מזה חצי מטר לפחות.** לפי טבלה 3-5 העוצמה המקסימלית שהמקלט
   סובל היא 0dBm — ואנחנו משדרים ב-5dBm. שני לוחות צמודים מרוויים אחד את השני,
   וזה נראה בדיוק כמו קישור מקולקל.
2. **החלף ערוץ** — `RF_CHANNEL` ב-[src/main.cpp](src/main.cpp#L23). הימנע
   מהערוצים 0, 16, 32, 48, 64 ו-80: הם כפולות של 16MHz (תדר הקריסטל) ולפי הערה 1
   בסעיף 3.3 הרגישות שם נופלת בערך ב-2dB. 78 הוא ברירת המחדל וגם ברירת המחדל של
   הצ'יפ, והוא נקי מהבעיה.
3. **הורד את `SPI_HZ` ל-`XN_SPI_HZ_SLOW`** אם ה-self-test עובר אבל לא באופן עקבי.

## ארבעה מקומות שבהם ה-XN297L לא תואם ל-nRF24L01

מפת הרגיסטרים נראית זהה ל-nRF24L01, ובגלל זה קל מאוד להעתיק דרייבר nRF24 ולקבל
צ'יפ שמדבר SPI מצוין ולא משדר כלום. ארבעת ההבדלים, כולם מסומנים במקום שבו הם
מוגדרים בקוד:

**1. `CONFIG` ביט 7 הוא `EN_PM`, וחייב להיות 1.**
זה ההבדל הקריטי. ב-nRF24 הביט הזה שמור-אפס. כאן, לפי טבלה 4-1, גם RX וגם TX
דורשים `EN_PM=1` — הוא מה שמעביר את הצ'יפ מ-standby-I ל-standby-III, ומ-STB3
בלבד אפשר להגיע ל-TX או ל-RX. דרייבר nRF24 מושאל משאיר את הביט הזה מאופס,
וה-`selfTest` עובר בשמחה בזמן שהרדיו לא מתעורר לעולם.

**2. `RF_SETUP` הוא 2 ביט קצב + 6 ביט הספק.**
קצב: `00`=1Mbps, `01`=2Mbps, `11`=250kbps. ההספק הוא **קוד 6 ביט מטבלה קבועה**
(`100111`=11dBm, `010101`=9dBm, `101100`=5dBm ...) ולא סולם 0–3 כמו ב-nRF24.
ערך "הספק מקסימלי" מקוד nRF24 נופל פשוט על צירוף לא חוקי.

**3. ה-reset הוא זוג פקודות, לא אופקוד בודד.**
`0x53` + `0x5A` מכניס את הצ'יפ ל-reset ו**משאיר אותו שם**; `0x53` + `0xA5` משחרר.
לשלוח `0x53` לבד זה לנעול את המודול.

**4. תקרת ה-SPI היא 1Mbps כל עוד הצ'יפ ב-power-down או standby-I.**
כל האתחול קורה במצבים האלה. `begin()` מאתחל ב-1MHz ומעלה ל-4MHz רק אחרי המעבר
ל-STB3.

בנוסף `FEATURE` נושא כאן `MUX_PA_IRQ` / `CE_SEL` / `DATA_LEN_SEL` שלא קיימים
ב-nRF24, וה-`FIFO_STATUS` בטבלת הדאטהשיט מופיע עם השמות והתיאורים של ביטים 0 ו-1
מוחלפים — לכן `available()` בודק את `RX_P_NO` ב-`STATUS` (שבו `111` = FIFO ריק)
ולא את `FIFO_STATUS`.

## הרגיסטרים האנלוגיים

ל-XN297L יש בלוק כיול שלא קיים ב-nRF24: `0x19` DEMOD_CAL (בית אחד), `0x1A`
RF_CAL2 (6), `0x1B` DEM_CAL2 (3), `0x1E` RF_CAL (3) ו-`0x1F` BB_CAL (5).

מתוכם **הדאטהשיט נותן ערכים רק ל-`BB_CAL`** — הוא מפרט את כל השדות שלו ואת ערכי
ה-reset שלהם. הרכבתי את הערך מהם ב-[src/xn297l.cpp](src/xn297l.cpp#L1-L27):
`0A 6D 67 9C 46`. השאר מופיעים במסמך כ-"Special Function Register" בלבד, עם
הפניה ל-software reference שאין לנו, ולכן **הקוד לא נוגע בהם ומשאיר את ערכי
ההפעלה**. עדיף מאשר לכתוב ניחושים לתוך ה-front end האנלוגי.

`BB_CAL` שווה לערכי ברירת המחדל, כך שהכתיבה אליו לא משנה כלום היום. הוא בקוד
כי שני תנאי התזמון של Enhanced BURST בסעיף 5.6 מנוסחים בדיוק בשדות האלה
(`TRX_TIME`, `EX_PA_TIME`, `TX_SETUP_TIME`, `RX_SETUP_TIME`, `RX_ACK_TIME`) —
זה המקום שאליו חוזרים כשקישור עובד ב-1Mbps ולא ב-250kbps.

## הצעדים הבאים לחיישנים

- **המטען הוא 32 בתים קבועים.** להחליף ל-`struct` עם הקריאות שלך. באורך סטטי
  מספר הבתים שנכתבים ל-TX FIFO חייב להיות שווה ל-`RX_PW_P0` בצד המקלט
  (סעיף 6.4.4) — הקוד מרפד באפסים ל-32 בדיוק בשביל זה.
- **אורך מטען דינמי** — צריך `EN_DPL` ב-`FEATURE`, את `DYNPD`, וגם פקודת
  `ACTIVATE` (`0x50` + `0x73`) כדי לשחרר את `R_RX_PL_WID`.
- **`IRQ` מחובר אבל לא בשימוש.** הפין הוא active-low ומתחיל גבוה (סעיף 5.9),
  והמסכות שלו ב-`CONFIG` ביטים 4–6 מאופסות, כלומר הוא כבר עובד — צריך רק לתלות
  עליו פסיקה במקום ה-polling.
- **צינור אחד (pipe 0).** יש שישה. שים לב שרק לצינורות 0 ו-1 יש כתובת מלאה של 5
  בתים; לצינורות 2–5 נקבע רק הבית הנמוך, והשאר משותף עם צינור 1 (טבלה 5-3).
- **הספק** — כרגע 5dBm. הטבלה המלאה ב-[src/xn297l.h](src/xn297l.h#L104-L110).
  11dBm מושך 66mA, וזה כבר דורש אספקה רצינית יותר מהרגולטור של לוח הפיתוח.
